# Raw ハッシュ設計メモ（prompt/input の sha256 は「生テキスト」に対して取る）

Status: 現行設計の記録（v3.6.5 で確定、PR #104 レビューで検証済み）
Related: `src/db.ts`（`sha256Hex` / turns 書き込み）, `src/redact.ts`, PR #104 レビューコメント

## 何の話か

ローカル DB（`.evo/evolutionary.db`）に保存する入力テキスト系のカラムは二系統ある:

| カラム | 内容 | マスキング |
|---|---|---|
| `turns.input_text` / `prompt_preview` / `output_preview` | 表示・調査用の本文（500 字 cap） | **保存前に `redactSecretText` で伏せ字化**（cap でのスライスより前に redact） |
| `turns.input_text_sha256` / `input_text_length`、各所の `prompt_hash` | 重複排除・メトリクス用の指紋 | **RAW（伏せ字化前）の全文に対して sha256 / length を計算** |

つまり「保存するテキストはマスク、ハッシュと長さは生」が意図した設計。

## なぜ RAW に対してハッシュするか

- **重複排除・メトリクスの正確性**: 同一プロンプトの再送を同一視するのがハッシュの目的。
  伏せ字化後のテキストでハッシュすると、`[REDACTED]` 置換の有無・パターン改訂のたびに
  同一プロンプトのハッシュが変わり、dedupe と履歴メトリクスが壊れる。
- **redact パターンは進化する**: v3.6.5〜3.6.7 でパターンを繰り返し強化した。redact 後
  ハッシュだとパターン更新 = 全履歴のハッシュ非互換になる。生テキスト基準なら安定。

## 脅威モデル（なぜ安全とみなすか）

PR #104 の独立レビューで確認済み:

- sha256 は一方向。**逆算可能性の主張はしていない**（rainbow claim なし）。
- ハッシュは**プロンプト全文**に対して取る。秘密値単体のハッシュではないので、
  「既知秘密値の辞書と突き合わせて存在確認する」型の攻撃が実用にならない
  （全文が完全一致しない限りハッシュは一致しない）。
- DB はローカル（gitignored `.evo/`）であり、`evo logs --bundle` などの持ち出し経路は
  テキスト側（redact 済み）だけを扱う。

### 残余リスク（既知・許容）

- プロンプト全文が**秘密値そのもの**（例: トークンだけを貼り付けた 1 行）だった場合、
  そのハッシュは秘密値単体のハッシュと一致する。低エントロピー秘密値なら理論上
  総当たりの対象になり得る。実運用上プロンプトは自然文+文脈であり、許容とした。
- `input_text_length` は生の長さを漏らすが、長さ情報から本文は復元できない。

## 将来この設計を変えるなら（メモ）

- 変更候補: ハッシュを HMAC（ローカル生成のインストール毎キー）にすると、DB 単体を
  入手した攻撃者による既知平文突き合わせを無効化できる。代償: キー紛失で全履歴の
  dedupe 連続性が切れる / キー自体の保管場所が新たな攻撃面になる。
- **変更する場合はマイグレーション必須**: 既存行の再ハッシュは不可能（生テキストは
  保存していない）ので、ハッシュ方式の世代カラムを足して新旧併存にするしかない。
- 現時点で変更の予定はない。この設計を変える PR は本メモの更新を必須とする。
